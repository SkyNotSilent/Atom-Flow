# AtomFlow 播客解读界面设计

日期：2026-07-17

状态：产品与视觉方向已确认，可进入实施

当前实施阶段：原项目内的前端界面与已有音频能力接入

## 1. 背景与已确认决策

AtomFlow 在“魔法写作”下增加独立一级入口“播客解读”。它是一个可上下浏览的音频知识流，不属于魔法写作画布的子模式。

用户确认采用视觉方向 C：

- 上半部分保留参考图里的封面、唱片和沉浸播放感。
- 下半部分持续显示当前观点、来源和知识库动作。
- 桌面端右侧展示章节、文字内容和来源依据。
- 实际实现直接进入 AtomFlow 原项目，不保留独立视觉稿的配色体系。
- 页面必须继承 AtomFlow 的浅色主题、深色主题、字体、边框和强调色。

内容同时支持短、中、长三种深度，而不是只做短卡或只做长播客：

| 层级 | 典型时长 | 内容形态 |
|---|---:|---|
| 知识切片 | 20 秒至 2 分钟 | 金句、关键观点、原则、数据、故事片段 |
| 主题速听 | 3 至 8 分钟 | 将同一事件或主题的若干观点串联 |
| 深度播客 | 10 至 30 分钟 | 单篇深读、多源今日总结、双人讨论 |
| 原生节目 | 来源实际时长 | 播放 RSS 原音频，并在后续阶段补充 AI 导览 |

双人表达是一种内容形式，不是所有卡片的硬性要求。短金句和数据卡可使用原声或单人朗读；主题速听和深度播客可使用主讲人加追问者。

## 2. 本阶段目标

本阶段先在原项目中完成可评审、可交互、可响应式展示的真实页面。

必须完成：

1. 在“魔法写作”下增加一级导航“播客解读”。
2. 页面采用全宽工作区，不显示现有文章阅读侧栏。
3. 使用当前 AtomFlow 主题变量和字体，而不是复制视觉稿中的独立珊瑚色主题。
4. 建立上下浏览的内容卡组，并同时表现短卡、主题速听、深度播客和原生节目。
5. 对 RSS 中真实存在 `audioUrl` 的节目提供真实播放、暂停、进度、快退、快进和倍速。
6. 对没有音频的文章显示真实的“待生成”状态，不模拟播放成功。
7. 右侧知识区使用现有文章标题、摘要和来源，不生成虚假的逐字稿或引用。
8. 提供移动端布局：主播放器占满页面，知识区改为底部抽屉。
9. 提供加载、空数据、无音频、音频加载失败和登录要求状态。

本阶段不修改数据库，不调用新的 TTS 服务，不创建后台生成任务，也不默认保存原始录音。音频生成、持久化语音记录和知识溯源属于后续数据阶段。

## 3. 信息架构

### 3.1 一级导航

左侧主导航顺序保持：

1. 今日推送
2. 发现订阅源
3. 我的知识库
4. 魔法写作
5. 播客解读

“播客解读”需要登录，因为内容会依据个人订阅、收藏和后续播放记录生成。

### 3.2 页面内部导航

页面顶部提供四个筛选：

- 为你生成
- 短知识卡
- 主题速听
- 深度播客

本阶段“为你生成”展示现有文章与原生音频。“短知识卡”“主题速听”“深度播客”保留完整界面和各自的空状态，但在生成接口上线前不使用启发式规则伪造分类。后续接口上线后，筛选值直接映射到 episode kind，不改变组件结构。

## 4. 桌面布局

AtomFlow 现有左侧导航保持不变。“播客解读”内容区内部使用两栏：

```text
┌──────────────────────────────────┬────────────────────┐
│ 沉浸播放区                        │ 当前内容与来源       │
│                                  │                    │
│ 封面 + 唱片                       │ 当前摘要/文字内容    │
│ 标题、来源、类型、时长             │ 来源文章             │
│ 进度与播放控制                    │ 章节或相关条目       │
│                                  │ 记录想法入口         │
├──────────────────────────────────┤                    │
│ 当前观点 + 打开原文 + 存入知识库   │                    │
└──────────────────────────────────┴────────────────────┘
```

布局规则：

- 主播放区占可用宽度约 65%，知识区约 35%。
- 播放区不是一个手机外框，而是适配桌面宽度的沉浸舞台。
- 封面和唱片是视觉焦点，但标题、播放状态和当前观点必须在首屏可见。
- 卡片组支持鼠标滚轮、触控板和上下方向键切换。
- 当前音频与当前浏览卡分离；浏览其他卡片不会自动停止正在播放的音频。
- 页面内只存在一个真实 `HTMLAudioElement`，避免多个卡片同时播放。

## 5. 移动端布局

- 顶部显示来源集合和返回按钮。
- 封面与唱片位于首屏上半部。
- 标题、时长、进度和播放控制位于中部。
- 当前观点位于播放器下方。
- 来源、章节和文字内容进入可上拉底部抽屉。
- 上下滑切换内容卡；拖动进度条、滚动抽屉和操作按钮不得触发换卡。
- 第一次播放需要用户主动触发。用户已主动播放后，是否连续播放由显式开关控制。

## 6. 主题与视觉规则

### 6.1 必须复用的现有设计令牌

页面外层和知识面板必须使用现有变量：

- `--theme-bg`
- `--theme-surface`
- `--theme-surface2`
- `--theme-border`
- `--theme-text-main`
- `--theme-text2`
- `--theme-text3`
- `--theme-accent`
- `--theme-accent-light`

文字继续使用项目已有的 Inter 与 Noto Serif SC。标题和当前观点可以使用 serif，控制和元数据使用 sans-serif。

### 6.2 沉浸播放区

播放区允许使用 AtomFlow 暖黑色中性色形成媒体空间，但必须遵循以下限制：

- 波形、当前进度和选中态使用 `--theme-accent`，不引入新的珊瑚色品牌主色。
- 边框、按钮、文字层级与当前深色主题保持一致。
- 浅色主题中，沉浸区作为局部深色舞台；页面背景、右侧知识区和导航保持现有浅暖主题。
- 深色主题中，舞台与页面背景通过边框和层级区分，不能成为一整块无层次的纯黑。
- 封面图可以拥有自身颜色，但不能改变页面控制组件的主题色。

### 6.3 动效

- 唱片只在真实播放时缓慢旋转；暂停时停止。
- 卡片切换使用短距离位移和淡入，不使用大幅弹跳。
- 波形进度变化控制在 150 至 220 毫秒。
- 遵守 `prefers-reduced-motion`，关闭唱片旋转和非必要过渡。

## 7. 内容与数据映射

本阶段复用 `AppContext` 的现有 `articles` 和 `savedArticles`，不在前端写死虚构节目。

### 7.1 原生播客条目

满足 `article.audioUrl` 的条目：

- 类型显示为“原生节目”。
- 使用真实 `audioUrl` 播放。
- 使用 `audioDuration` 或浏览器读取的媒体时长。
- 右侧显示 RSS 摘要、来源和原文链接。
- 不声称已经生成 AI 章节或完整转写。

### 7.2 普通文章条目

没有 `audioUrl` 的文章：

- 类型显示为“文章待解读”。
- 封面使用现有文章图或基于来源生成的主题封面。
- 展示标题、来源、发布时间和 RSS 摘要。
- 主按钮显示“生成解读”，并明确标记音频生成尚未接入。
- 不显示可拖动的虚假播放进度。

### 7.3 空状态

当天没有可用内容时：

- 显示“今天还没有可收听内容”。
- 提供“查看过去 3 天”和“前往发现订阅源”。
- 不使用固定演示内容填充生产页面。

## 8. 组件边界

建议新增：

```text
src/pages/PodcastPage.tsx
src/components/podcast/PodcastStage.tsx
src/components/podcast/PodcastCover.tsx
src/components/podcast/PodcastControls.tsx
src/components/podcast/PodcastInsightPanel.tsx
src/components/podcast/PodcastContextPanel.tsx
src/components/podcast/PodcastCardRail.tsx
src/components/podcast/podcastPreview.ts
```

职责：

- `PodcastPage`：数据筛选、当前条目、响应式布局和页面级状态。
- `PodcastStage`：封面、唱片、标题、标签和沉浸舞台。
- `PodcastControls`：唯一音频元素、进度、倍速和错误处理。
- `PodcastInsightPanel`：当前摘要、打开原文和知识动作。
- `PodcastContextPanel`：来源、章节占位状态和文字内容。
- `PodcastCardRail`：卡片切换、键盘和滚动导航。
- `podcastPreview`：将现有 `Article` 映射成前端展示模型，不负责生成内容。

初始展示模型：

```ts
type PodcastPreviewItem = {
  id: string;
  articleId: number;
  kind: "native_episode" | "article_pending";
  title: string;
  source: string;
  publishedAt: string;
  summary: string;
  imageUrl?: string;
  sourceUrl?: string;
  audioUrl?: string;
  audioDuration?: string;
};
```

后续新增 `PodcastEpisode` 接口时，页面组件继续消费同一类展示模型，避免重写布局。

## 9. 播放与交互状态

播放状态：

- `idle`
- `loading`
- `playing`
- `paused`
- `error`

规则：

- 切换到另一个有音频的条目时，只有用户点击播放才替换当前音频。
- 切换到无音频文章时，当前音频可以继续播放，并以迷你状态显示正在播放的原节目。
- 音频 URL 加载失败后保留标题和来源，显示重试与打开原节目按钮。
- 进度只在真实音频加载成功后显示。
- 卡片的“存入知识库”复用现有保存文章能力；后续再升级为保存节目和具体片段。
- “说下我的想法”本阶段作为明确入口展示，但只有在持久化语音记录规格完成后才开放长录音；不能把现有短听写包装成长时录音。

## 10. 无障碍与响应式要求

- 所有控制提供可读的 `aria-label`。
- 播放、暂停、快退、快进和倍速可键盘访问。
- 使用真实按钮，不以可点击 `div` 替代。
- 当前筛选、当前卡片和当前播放状态不能只靠颜色表达。
- 封面图片提供基于标题的替代文本。
- 文字和控制在浅色与深色主题下均满足可读对比度。
- 右侧面板在窄于桌面断点时转换为抽屉，不直接隐藏关键来源信息。

## 11. 错误与诚实性原则

- RSS 摘要不能标成完整转写。
- 没有调用过生成服务的内容不能显示“AI 已生成”。
- 没有真实音频时不展示会动的播放进度。
- 只有摘要的内容明确显示“基于 RSS 摘要”。
- 原生节目与 AI 解读使用不同标签。
- 浏览器不支持音频格式时提供原节目链接。

## 12. 后续阶段

本界面稳定后按以下顺序接入数据能力：

1. 真实阅读状态和稳定文章身份。
2. Podcast Episode、来源、分段、任务和播放进度模型。
3. 对象存储与异步生成任务。
4. 短内容 TTS、双人深读和供应商适配器。
5. 持久化实时语音记录、逐段转写和知识库来源关系。
6. 每日定时生成与跨页面持续播放。

供应商不写死在前端。当前推荐方向仍为：短中文朗读优先评测 MiniMax，双人长内容评测火山播客模型，实时语音识别升级火山 ASR；最终选择由中文盲测、正式报价和 Railway 连通性决定。

## 13. 验收标准

界面阶段完成时必须满足：

1. “播客解读”出现在“魔法写作”下并可正常进入。
2. 页面使用真实 AtomFlow 主题令牌，浅色和深色模式均无明显冲突。
3. 桌面端呈现方向 C 的播放器加知识层布局。
4. 移动端能够上下浏览，来源面板可通过抽屉访问。
5. RSS 原生音频可以真实播放，且页面内不会出现多个音频同时播放。
6. 无音频文章显示诚实的待生成状态。
7. 空数据、加载失败和音频失败均有明确状态。
8. `npx tsc --noEmit`、`npm run lint` 和 `npm run build` 通过。
9. 浏览器检查覆盖桌面、移动、浅色、深色和 reduced-motion。
10. 完成项目要求的 quality-gate 与 code-reviewer 评审，并直接修复发现的问题。
